## Goal

More independently verified tasks per unit of ChatGPT subscription usage on `openai-codex`, without weakening safety. Progress is measured on the same tasks against Droid running the same model and effort into the same ChatGPT Codex backend.

Matching Droid's feature list is not the goal. A Droid mechanism is adopted only when a measured gap points to it, and only through the plan that already owns that part of DaVinci.

## Decisions taken

- **D1. Comparison route.** Droid 1.1.0 runs through CLIProxyAPI. DaVinci runs on its production backend route, `/login openai-codex`, which goes to `chatgpt.com/backend-api/codex` over WebSocket. Both arms use the same ChatGPT account, model and effort. The class is `product-system`, with the proxy recorded as a known confounder. A DaVinci-through-proxy arm is rejected: DaVinci's capability resolver gives a localhost HTTP endpoint no route features (`codex_capabilities.rs:121-162`), so that arm would not represent DaVinci.
- **D2. Arms.**
  - **DaVinci-default:** the user's `/config`, with the Codemode and Context VM modes recorded.
  - **Droid-direct:** `--tool-execution-mode direct-only`.
  - **Droid-script:** `--tool-execution-mode script-only`.

  Droid's own default for a proxy alias is uncertain: canonicalization of custom aliases is unresolved (ch. 18 §9). So both Droid modes are forced, and the resolved mode is recorded from the session settings. The two Droid arms together supply the real-model Script-vs-direct result (A1–A3) that the reference could not run.
- **D3. Model.** `gpt-6.1-sol`, high effort. It is on Factory's Script-default list and on this account's allow-list, and it is the model Factory used for its Droid–Codex comparison. Earlier DaVinci evidence on `gpt-6-luna` does not carry over. If the user prefers `gpt-6-luna` for continuity, swap it at approval time. Factory's Script-default list omits luna, so a null Script result on luna would not generalize.
- **D4. Corpus.**
  - `verified-core`: 6 Rust tasks, graded by `cargo test` (`crates/davinci-evals`).
  - The 8 public bench tasks from `C:\bench\pubcmp`, graded by their task tests.
  - Research fixtures 01–03 from `C:\Users\sergi\Desktop\lean-droid-1.0\droid-re-research\fixtures`, graded by artifact-only `grade.ps1`.

  That is 17 tasks. The public tasks have two weaknesses:
  - Their fixtures expose graders and solutions (`fixture_secrecy`, `docs/perf/codex-efficiency/promotion-decision.md`), so they give direction only.
  - They were used in DaVinci tuning, which biases them toward DaVinci, so a Droid win on them is conservative.

  New tasks need an independent author (the H1 rule). Fixtures 04–11 test Droid-specific Script semantics and are kept as mechanism probes only.
- **D5. Budget.** At most 120 live runs for the whole program unless re-approved. Each live step needs its own approval naming the runs, pins and model. Stage 0 uses at most 55 runs.
- **D6. Placement.** When this lands in the DaVinci repo, it goes to `docs/superpowers/plans/2026-10-31-droid-gap.md`, with evidence under `docs/perf/droid-gap/`. Code changes are written into the owning plan's execution record, not here.

## Stage 1 — Close measured gaps

Each workstream lists its trigger, owner, mechanism, change and confirmation. A workstream with no fired trigger is closed. **S1** and **S2** are the exceptions: they need no trigger because they fix correctness hazards found in this review, and they are offline and small.

### S1. Wire the dead loop-stop signals (no trigger; offline)

- **Owner:** `runtime/progress_watchdog.rs`.
- **Mechanism:** the watchdog computes repeated-command, repeated-read and oscillation signals in 3-wide windows. They only set `Paused`, which nothing in the live path reads (`can_dispatch` is test-only, and `apply_watchdog_choice` is `#[allow(dead_code)]` at `davinci_interactive.rs:3806`). Only repeated test failures act: a reminder, then a stop (`turn.rs:745-780`). An identical-read loop can therefore run to `maxModelTurns` = 200 (`lib.rs:948`). Droid nudges at 3 and stops at 6, observed at runtime (ch. 19 §5.1).
- **Change:** route the existing signals through the existing `RepairAction` path: a nudge at the first signal, a stop at a second signal on the same digest. A call returning new evidence (`has_new_evidence`) or a job poll (`is_job_poll`) is exempt. Keep the thresholds as constants beside the existing ones. Do not copy Droid's numbers as a target.
- [x] Tests: unit cases in `progress_watchdog.rs`, plus one turn-level test with the fixture provider in `turn.rs` tests. One test checks a polling loop that keeps returning new output is not stopped.
- [x] Verify: `cargo test -p davinci-agent progress_watchdog` and the new turn test, then fmt. Clippy and one full `davinci-agent` run go before the PR.

### S2. Codemode output keeps the tail (no trigger; offline)

- **Owner:** the Codemode plan, item C05 (amend its execution record).
- **Mechanism:** over the 16 KiB model budget, Codemode keeps the head and drops the tail (`supervisor.rs:884-891`), and `output_artifact` is always `None` (`:903`). An error at the end of a log is lost. Droid keeps head and tail with a marker (ch. 03 §5).
- **Change:** keep head and tail with an explicit omitted-bytes marker, and keep `Partial` plus the host note.
- [x] Tests: extend `codemode_supervisor_budget.rs` with an error at the tail.
- [x] Verify: `cargo test -p davinci-coding-agent --test codemode_supervisor_budget`, then fmt.

### W1. Completion exit gate

- **Trigger:** the Stage 0 success gap is "stopped early or claimed done unverified".
- **Owner:** `completion.rs` and the turn completion gates (`turn.rs:1221-1342`), reusing the PR #259 receipts.
- **Mechanism:** DaVinci ends the run on any reply without a tool call (`turn.rs:1412`). ### W2. Tool surface size and mid-session activation

- **Trigger:** P0.2 shows DaVinci's first request materially larger than Droid's, and Stage 0 labels total or uncached input `GAP`.

  - Lean was measured live on 2026-09-25: 21/24 passes at 74.2% cache, and it was not promoted (`docs/perf/openai-speed-results.md:33,79`).

### W4. Pruning and compaction cost

- **Trigger:** DaVinci's prefix-break log in Stage 0 concentrates uncached input after pruning or compaction on long tasks.
- **Owner:** codex-efficiency plan, Task 8, and `docs/context-vm.md`.
- **Mechanism:**

## Stage 2 — Defaults and claims

- A default changes only through its owner plan's promotion gate (`davinci-evals/src/promotion.rs`, `docs/perf/codex-efficiency/promotion-decision.md`), using the promotion ledger below.
- An efficiency default needs a preregistered paired A/B where the ratio interval clears the 0.85 rule, there are no pass regressions, every discordant task is inspected, and the security tests pass.
- Head-to-head superiority claims against Droid follow `docs/competitor-benchmarks.md`: at least 150 shared scenarios × 3 repetitions. That costs about 900 runs and is outside this program's budget. Stage 0 results are described as a measured gap on 17 tasks, not as parity or superiority.

## Corrections to v1 facts

- **Droid limits are not DaVinci limits.** "5 MiB" and "1,024 events" are Droid figures. DaVinci's Codemode limits are:

  | Limit | Value |
  |---|---|
  | Child result | 1 MiB |
  | Collected output | 1 MiB |
  | Total results | 8 MiB |
  | Output to the model | 16 KiB |
  | Text and console items | 100,000 |
  | Script and arguments | 64 KiB each |
  | Wall | 60 s, hard kill |
  | Calls / parallel / pending | 64 / 4 / 64 |

  Source: `codemode/mod.rs:23-44`, `supervisor.rs`.
- **Controlled mode is not "enum-only".** The broker and policy already admit it, and tests exercise it. Production hardcodes `ReadOnly` (`execution.rs:196`), and the CLI refuses Controlled (`config.rs:46-50`).
- **There is no `riskLevel`.** Neither the string nor "shell risk metadata" appears in DaVinci.
- **"Attach to the jobs supervisor" names the wrong owner.** `jobs/supervisor` supervises OS processes. The Codemode host is an in-process child, and job notices are injected only inside an active turn.
- **Nothing sorts tools alphabetically.** Order is declaration order, then MCP, then registry. Full never diverges, because every schema is frozen up front (`lib.rs:4580-4630`).
- **The backend's cache key is not gated on route confirmation.** It is sent whenever retention is not `none` (`stream.rs:2100-2105`), and WOR-33 validated that.
- **Native compaction is not an option on this route.** `remote_compact` returned 404 and `server_side_compaction` is false.
- **The competitor gate lacks what v1 assumes.** It has no usage fields and an unconditional 3 pp margin (non-inferiority is hardcoded `false`, `main.rs:1424`). Its challenge corpus has no verification commands, and DaVinci always runs first.
- **`behavior-evals.yml` cannot run providers.** It runs only offline `cargo test` and is gated to `earendil-works/pi` unless dispatched.
- **`first_prefix_break` is in `davinci-agent`** (`cache_stability.rs`), not in `davinci-ai`.
- **The real corpus command is `cargo run -p davinci-evals -- corpus validity [--report PATH]`.** It covers only `verified-core` and `core-200`. v1's core-200 counts (0 verified, 110 structural-only, 90 invalid) are correct.
