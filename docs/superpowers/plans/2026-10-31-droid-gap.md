## 2. Behavior parity vs performance parity

- **Behavior:** the deterministic surface is proven; the program-level claim is
  **not** made because detached runs are unapproved and image output is a
  declared gap. `behaviorParity` is recorded as `false` in
  [stage1-promotion.json](../../perf/droid-gap/stage1-promotion.json).
- **Performance:** Stage 0 was a 17-task pilot (Droid Direct 12, Script 11,
  DaVinci 10 passes; 247/111/88 requests). That is not a parity proof, and no
  matched suite (≥150 scenarios × 3 repetitions) or independent allowance
  measurement was run. Every such claim is refused by
  `scripts/bench/parity_report.py`.
- **Transport confound:** DaVinci runs native WebSocket, Droid goes through a
  proxy. Any comparison is `product-system` unless that confound is bounded.

## 3. Promotion decision

`rollout_gate(PromotionDecision { behavior_parity: false, security_pass: true,
success_noninferior: false, resource_benefit: false, unknowns: [...] })`
returns **`off`**. Concretely:

1. Keep `off`/direct default; keep read-only Codemode as-is.
2. Do not default-enable controlled Script.
3. Do not claim Droid parity, performance parity or subscription savings.
4. Ship the opt-in plumbing behind the existing release gate
   (`CONTROLLED_RECOVERY_ACCEPTED = false`).

## 4. Rollback

Set `"codemode": {"mode": "off"}` or remove the key. Later turns no longer offer
or run Codemode. Durable run records under `<evidence dir>/script-runs` stay in
place and are never replayed; an unresolved mutation stays
`recoveryRequired` and must be reconciled from the operation journal. See
[`docs/codemode.md`](../../codemode.md).
