DaVinci Codemode
Implementation Plan
For agentic workers: Use superpowers:executing-plans to
implement this plan task-by-task. Use superpowers:subagent-driven-development only when the user explicitly selects that
execution method. Steps use checkbox (- [ ]) syntax for tracking.
Do not start implementation merely because this document exists.
Goal: Add optional, sandboxed JavaScript tool orchestration to DaVinci
so a model can perform bounded, data-dependent tool calls, filtering,
and aggregation inside one model-visible operation, without bypassing
DaVinci's permissions, evidence, recovery, or Token Governor.
Architecture: Keep the Rust harness authoritative. Run Pi's standalone
QuickJS/WebAssembly Codemode package in a separate, trusted,
optional Node host process; forward every nested tool request to the
Rust dispatcher. Preserve structured results for the script and present
only bounded script output plus host-authored execution facts to the
model.
Tech stack: Existing Rust 1.83.0 workspace, existing session/operation
journal, capability registry, scheduler, process supervisor, MCP client,
Token Governor, and output artifacts. Proposed sandbox package pins:
@earendil-works/pi-codemode@1.0.2 and its quickjs-wasi@3.6.2 dependency. Optional Node runtime satisfying the
package's >=22.19.0 requirement; use a security-maintained release,
not an old minimum merely because it satisfies the range. Exact runtime
and complete dependency-lock identities are admission evidence in
Task C01.
Spec: The embedded design contract in Sections 1–12 of this
document. It travels with the implementation tasks; there is no separate
dependency on a general Pi-upgrade plan.

system/tool configuration, virtual models, cache warming, Pi
Durable, a UI redesign, or a broad Pi dependency upgrade.
• Preserve the existing Rust 1.83.0 toolchain and exact Rust

generic workflow engine is required by this design.
• Preserve ChatGPT-subscription use through openai-codex;
introduce no API-key requirement, paid-model dependency,
alternate auth route, or API fallback.
• Preserve the user's selected model, reasoning effort, and service

or hidden model requests inside scripts.
• Retain Token Governor, its recovery access, Context VM,
compaction, existing artifacts, batch, ordinary tools, and Full/
Lean defaults.
• Normal DaVinci usage must not require Node because Codemode
was added. Codemode itself has an explicit optional Node
requirement. Missing runtime/assets disable only this feature.
• Rust, not JavaScript, decides authorization, argument validity,
resource budgets, dispatch, effect classification, cancellation, and

recovery.
• All nested tool calls must pass the same applicable safety hooks,

• Ordinary model-facing result behavior stays unchanged when

Review focus
1. A permitted-looking tool becomes forbidden while queued:
dispatch must recheck current authority; stale discovery is not
approval. Covered by C04/C07.
2. An earlier write succeeded before the script failed or the
process died: no automatic script replay, false rollback claim, or
hidden second mutation. Covered by C07/C08.
3. A governor digest or truncated MCP payload looks like
complete input: the script must receive an explicit complete/
incomplete value and an authorized recovery route, not fabricated
structured data. Covered by C03/C05.
4. A Windows path, Unicode identifier, or colliding JavaScript
alias points at the wrong executable/tool: use canonical
identities and explicit collision rejection. Covered by C01/C02/C04.
5. A script catches errors or prints a fabricated success report:
host-authored child outcomes and verification evidence cannot be
overwritten by script output. Covered by C06/C08/C10.

1. Intended outcome and scope
The desired workflow is not merely “run JavaScript.” It is: discover
relevant authorized tools, call them, use returned values to decide the
next calls, perform deterministic local filtering/joining/aggregation, and
return evidence-sized results to the selected model. Ordinary coding and
semantic judgment still belong to the model and existing tools.
A useful example is collecting a pull request's changed files, fetching
related checks, following pagination until a bounded condition is
satisfied, and returning only failed checks with file references. The script
should not need another inference just to pass a cursor from one
response to the next. It must not claim that a PR is safe merely because
its filter returned an empty list.
In scope
• One model-facing codemode tool using ordinary JSON tool
arguments.
• JavaScript await, return, bounded output, ordinary loops, and
bounded parallel calls.
• Built-in, MCP, and registered native/JavaScript-extension leaf
tools, subject to the parent's existing authority and the Codemode
policy.
• Structured MCP preservation and an explicit script-facing result
envelope.
• Per-child permission checks, hooks, operation receipts,
cancellation, tracing, and conservative recovery.
• Read-only and explicitly enabled controlled execution;
deterministic bounded output; existing artifact retrieval.
• Existing CLI/TUI, print/JSON, RPC, and SDK entry points, with
explicit capability absence when a host is not installed.
• Documentation, installation of optional sandbox assets, native-Windows validation, and comparison against the existing
optimized baseline.
Out of scope


<!-- Source PDF page 5 of 57 -->


• A new root-model router, model API, authentication flow, provider
wire feature, model downgrade, or subscription accounting
formula.
• General dynamic system-prompt/tool-configuration events or a
global tool-exposure redesign.
• Persistent JavaScript heaps, VM snapshots, a cross-session
object database, or resumable script instruction pointers.
• Pi's non-LLM models helpers, image() product support, code-generated subagents, nested workflows, or nested Codemode.
• Replacing the Token Governor, reimplementing compaction, or
adding a second execution journal.
• Automatic retries of whole scripts, automatic Git commits,
deployments, or a guarantee that multiple nested writes are one
atomic transaction.
• A Bun-native packaging project or a new installer/update service.
Bun support can be evaluated later without making it part of the
first release's acceptance.
Persistent-state boundary: V1 starts a fresh VM for every invocation.
Upstream store/load, where present, are invocation-local scratch
only: initialize an empty store each time and discard storeWrites.
State does not survive another invocation. This is documented, tested,
and not represented as full Pi feature parity. Normal tool arguments/
results and operation evidence remain persisted through DaVinci's
existing mechanisms. A later persistent Codemode store would be a
separate, narrowly scoped change, not a prerequisite here.

4. Product contract
4.1 Feature selection
Proposed launch flag:
--codemode off|read-only|controlled
Proposed user settings:
{
 "codemode": {
 "mode": "off",
 "nodePath": null,
 "hostPath": null
 }
}
off is the default. nodePath and hostPath are user/host-controlled
absolute paths, not model arguments. Workspace settings cannot
elevate this feature, replace its host, or raise limits. A launch-time explicit
choice may enable the feature; existing global configuration/trust
precedence must be preserved. The feature mode is not a replacement
for DaVinci's permission mode.
• off: no schema, host lookup, subprocess, sandbox-assets scan,
extra prompt text, or model call.


<!-- Source PDF page 11 of 57 -->


• read-only: script calls only host-classified read-only leaf
capabilities permitted to its parent. Unknown effects are not read-only. Planning mode never gains mutations.
• controlled: child tools may mutate only through the ordinary
permission, transaction, supervisor, and journal boundaries. A
durable operation root is required. Missing durable state rejects
controlled execution before starting the script.
Effective permission is always the intersection of parent authority,
current tool selection, Codemode's restrictions, current project trust, and
the normal per-call approval. Codemode cannot grant authority.
No codemode-only mode is added in V1. Ordinary tools and batch
stay available. No automatic change from Full to Lean occurs.
4.2 Model-facing input
Use a regular function-tool schema on every supported provider route;
do not introduce raw-code custom-tool wire formats or provider-native
tool-search fields.
{
 "code": "const r = await tools.read({path: 'package.json'}); return JSON.parse(r.text).name;",
 "timeoutMs": 60000,
 "maxOutputBytes": 16384
}
Required: non-empty code. Optional values can reduce a host limit,
never raise it. timeoutMs must be an integer from 1,000 ms through
the effective host deadline; maxOutputBytes must be an integer from
4,096 bytes through the effective host output limit. Reject unknown
fields, negative/fractional values, oversized UTF-8 input, and
unsupported option-header directives before executing. // @options:
is not a supported control channel in this version: reject it rather than
maintaining two competing option systems. Ordinary comments remain
allowed.
The initial guest tool catalog is capped at 1,024 eligible tool names and
512 KiB of descriptors. Send compact names/descriptions, not every full

input schema. If the catalog exceeds the ceiling, refuse with a request
for a narrower explicit tool selection rather than silently omitting eligible
capabilities. describeTool obtains a bounded exact schema when
needed.
The static description states: use direct tools for simple operations,
batch for known independent operations, and Codemode for data-dependent orchestration or substantial deterministic projection. Keep
core instructions and helper signatures within 8 KiB UTF-8. Do not paste
the entire live tool registry into the provider prefix.

• tools.<safeIdentifier>(args) and canonical bracket
access for eligible, uniquely mapped tools.
• await, return, ordinary JavaScript computation, Promise.all,
and Promise.allSettled.
• text(value) and console output, subject to bounded

• An invocation-local store/load compatibility surface only as

Do not inject provider credentials, environment, filesystem, network,

Build the candidate tool set from the parent-authorized runtime registry,
not a process-global registry. Remove denied, unavailable, internal-only,
and explicitly excluded capabilities before producing guest metadata.

5. Script-facing results and Token Governor
integration
5.1 Normalized envelope
Every successful nested call resolves to the same envelope shape,
irrespective of whether it came from MCP or a native tool:
type CodeModeToolValue = {
 text: string;
 structuredContent: unknown | null;
 complete: boolean;
 artifact: { id: string; kind: "tool-output"; bytes: number } | null;
 operationRef: string;


<!-- Source PDF page 14 of 57 -->


};
This is a DaVinci API decision, not Pi wire parity. operationRef
identifies host evidence; it is not an authorization token. Built-in text tools
normally set structuredContent: null. MCP structured results
survive decoding, dispatch, and bounded projection. Do not assume
text is JSON; the script may deliberately parse known text.
Failed tools reject with a bounded typed error carrying a stable code and
operation reference. Partial data may be available through an authorized
artifact, but a failure does not become a successful empty array.
Transport timeout after a possible external effect is distinct from a
validation failure before dispatch.
5.2 Preserve structured data at its actual source
Extend davinci-mcp::CallToolResult to retain optional
structuredContent, and preserve optional outputSchema in the
tool definition. Keep existing direct-call text() output unchanged. Audit
and update struct literals/tests made incompatible by added Rust fields;
do not assume a Serde default makes Rust struct construction source-compatible.
Do not stuff raw result data into arbitrary ToolResult.details and
hope it stays private: that field is used by UI/events, and server-supplied
data must not forge host fields such as replay/commit flags. Introduce an
explicitly host-owned script-delivery channel at the shared execution
boundary. MCP _meta, private transport data, auth material, and
arbitrary new server fields are not automatically guest-visible.
5.3 One semantic path, two delivery projections
The common execution path produces authoritative outcome/evidence.
Afterwards it may deliver:
• Model delivery: the existing Governor/model presentation,
unchanged for direct tools and batch.
• Script delivery: a bounded, structured, authorized value before


<!-- Source PDF page 15 of 57 -->


model-specific digest/truncation, while retaining safety vetoes,
redaction, freshness, and receipts.
A third-party post-hook may transform or redact content. If the host
cannot prove an independently captured structured payload reflects that
transformation, drop structured delivery for that result rather than expose
pre-redaction data. Never send a pre-hook secret because the tool also
supplied structured JSON.
Governor compression, read deduplication, and anti-loop behavior need
explicit consumer semantics. The script must not receive a “see previous
output” digest as if it were the requested file. Rehydrate a permitted,
fresh exact output where the existing store supports it; otherwise run the
ordinary safe read again or report an explicit incomplete/error result. Do
not weaken source freshness or permission rechecks to avoid an extra
read.
Intermediate raw results remain bounded and, where retained, live in
existing evidence/artifact storage rather than model messages. Large
structured JSON must not be cut into invalid JSON. If it exceeds the
bridge limit, return complete: false, structuredContent: null,
and a recoverable artifact reference; require paging/refinement before
semantic use. Artifact access is separately authorized, session/
workspace-bound, and size-limited. Cross-session or stale references
never confer permission.
The final Codemode envelope is processed by the existing Governor
once. Reserve the mandatory host-note budget before truncating script
text. Permitted output between the model-visible limit and the 1 MiB
collection limit may use existing artifacts; output beyond the collection
limit is reported as not fully retained. Never emit a fabricated full-output
reference. Protect host-authored failure/completeness/recovery notices
from lossy presentation. Governor storage failure follows its existing
direct-tool behavior, but Codemode still enforces its own bridge/output
hard limits; fail-open compression must not mean unlimited IPC or an
unbounded prompt.

7. Authority, scheduling, and mutation
semantics
Extract a small common child-call driver from the existing direct/batch
patterns instead of inventing a second execution stack. It must cover
preparation, authorization, hooks, operation admission, rechecks,
scheduler lane selection, cancellation, actual tool dispatch, post-hook
observation, mutation paths, verification observation, receipt recording,
and result publication. Preserve the current ordering contract; do not
move journal admission after an external effect. [R3, R8]
The Codemode parent is an orchestrator, not a global write lock. It must
not hold a tool-execution permit, journal mutex, agent mutex, or mutation
lease while a nested call or approval waits. Child work participates in the
same existing lane/resource rules as direct calls. Otherwise a parent
awaiting its children can deadlock its own scheduler.
Independent reads can overlap. Mutations use normal serialized/
exclusive rules, preserving invocation order at the broker where ordering
is required. A script doing Promise.all([writeA(), writeB()])
does not create parallel-write permission. Respect per-server MCP
serialization already present; do not promise parallelism through one
server connection when the client serializes it. [R5]
Revalidate current permission/trust and adapter availability immediately
before dispatch. A late MCP reconnect/tool-definition change invalidates


<!-- Source PDF page 19 of 57 -->


the invocation's matching capability snapshot; stop affected calls and
require a fresh invocation instead of silently rebinding a canonical name
to a different tool. Discovery helpers may describe only currently eligible
tools.
Approval prompts show the actual nested tool and arguments, the
parent Codemode operation, and current normal approval context.
“Approve this script” must never authorize arbitrary future arguments.
Background/non-interactive calls needing approval return the existing
denied/unavailable-approval behavior, not automatic acceptance.
Successful child writes are real. A later script exception does not undo
them. The result must identify completed, failed, cancelled-before-start,
and unresolved children. Ordinary file transactions keep their existing
individual rollback behavior; no whole-script transaction is promised.
8. Journal, retries, cancellation, and
continuation
Use the existing operation journal as the sole execution authority.
Persist parent intent before starting the host. Bind each child to the
durable parent plus a host-assigned ordinal/request mapping and
normalized argument digest. A duplicate IPC request with the same
identity/payload reuses the existing outcome; a changed payload under
that identity is a collision and is rejected.
Host identifiers, parent lineage, workspace, authorization revision, and
effect classification are never chosen by the guest. A request ID is a
correlation field, not permission to execute or to pick another session's
operation.
Do not resume JavaScript automatically after a crash. JavaScript
branches may depend on changing external data, completion order,
time, and previously returned values. Re-running a script and hoping the
same child ordinals occur is not a valid replay strategy.
Recovery rules:


<!-- Source PDF page 20 of 57 -->


1. Completed parent: replay the recorded presentation/result only
after current access checks; do not execute the VM again.
2. Interrupted parent before any effect: report interrupted; a fresh
user/model retry is a new invocation, not silent continuation.
3. Completed child plus incomplete parent: retain and report the
child's evidence. Never silently repeat it under a new ID.
4. Child may have acted but lacks conclusive outcome: retain
RecoveryRequired; use existing reconciliation. Fresh IDs must
not evade unresolved claims.
5. Host/VM failure: stop admission, request child cancellation,
preserve partial output and host facts, supervise process cleanup,
and record actual known effect state.
6. Script returns with live child calls: stop new work, request
cancellation, drain observed outcomes, and report unawaited calls
explicitly. Do not report a clean complete result while effects
remain unknown.
7. Mode off or old binary: stored Codemode results remain readable
as ordinary tool text/evidence. Reading history never evaluates
stored scripts.

16. Rollout, rollback, and stopping rules
1. Internal fixture-only: admit assets and broker, no production
exposure.
2. Opt-in read-only: enable only after the C06 milestone and its
safety prerequisites.
3. Opt-in controlled: enable after C08 crash/recovery gates and


<!-- Source PDF page 53 of 57 -->


current authority parity.
4. Packaged optional release: enable availability after C12's actual
platform/packaging evidence; keep default Off.
Rollback is --codemode off or its explicit user setting, then a normal
restart/new invocation. Stop and reconcile in-flight work through the
existing runtime; do not delete journals or clear unresolved effects.
Remove optional host assets only after no owned process uses them.
Retain normal tool results, operation evidence, and output artifacts
under the existing retention rules.
Stop or keep the candidate experimental when:
• the standalone package/runtime cannot meet the security-maintained dependency or platform contract;
• the only way to integrate a tool is to bypass hooks, authorization,
result redaction, or durable recovery;
• host buffering, child calls, or process cleanup cannot be bounded
as documented;
• structured results are discarded before the script or substituted
with apparently complete summaries;
• throughput improvements require unsafe parallel writes, hidden
requests, disabled Governor, changed models, or omitted failures;
• measured end-to-end benefit is absent or startup/repair/retrieval
overhead consumes it;
• implementation starts adding a model router, persistent VM
service, new journal, general transcript configuration, or paid-model API to justify the feature.
An optional read-only implementation can remain useful even when
controlled mode has an unpassed gate. Label that boundary explicitly;
do not present a partially enabled feature as full completion.
