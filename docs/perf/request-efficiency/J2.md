# J2 — deterministic requirement ledger and routing boundary

Status: **deterministic requirement checks implemented; Jev completion and
family-routing arms remain unpromoted**.

`RequirementLedger` is derived from the already redacted task, bounded to eight
records and 240 characters per wording. Each record has a stable hash ID and
the ledger marks overflow or truncation incomplete. Requests add one bounded
Choice question per enumerated requirement, in the same decision request as
the existing capability, scope, and risk questions. No separate planning round
is introduced.

`deterministic_requirements_satisfied` is fail-closed. Every requirement needs
current, passing, concrete evidence with a reference and a Check, Observation,
or Diff kind. Missing, failed, stale, comment-only, unavailable, and truncated
evidence remain incomplete regardless of provider confidence. `RequirementAdvice`
preserves the Task 13 freshness key and has no provider-created evidence
references, so a provider judgment can add a reminder but cannot waive a hard
requirement.

The labeled unit cases cover: complete change, omitted requirement, incorrect
boundary after a smoke pass, stale diff, failed command, truncated requirement
set, misleading diff comment, and unavailable evidence. The reserved
`completionAdvice` and `toolFamilyAdvice` settings are false by default. No
0.85 completion threshold, blocking family arm, hidden-grader result, or
calibration claim is made.
