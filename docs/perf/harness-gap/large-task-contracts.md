# Large-task contracts (m1–m4): audit and v2 proposal

Date: 2026-10-15. Status: **proposal only.** No fixture, grader, reference,
manifest or campaign was changed. The v1 tasks generated by
`scripts/bench/make_large_tasks.py` and their hashes in
`scripts/bench/large_manifest.json` stay frozen as historical evidence; v2 would
be a new, separately identified task set whose results are never pooled with v1.

This refines [benchmark-integrity.md](benchmark-integrity.md). That audit listed
the tasks every run failed. This one classifies each hidden test by what its
failure can establish, and checks the claims by running code.

## Method

In a scratch directory outside the repository, each v1 task was materialized
from `TASK_SPECS` as starter or reference, then single-line variants of the
reference were run against the hidden tests with pytest. No model, campaign or
generated `scripts/bench/tasks/` tree was involved.

| Probe | Hidden result |
|---|---|
| Each starter | fails (m2: collection error, `render_user` missing) |
| Each reference | passes, and passes its own public test |
| m4 reference against the **starter** public test | public `test_legacy_total` fails |
| m4 reference with `total` kept as addition | only `test_legacy_total_still_works` fails |
| m4 reference whose `main()` returns 2 instead of raising | `test_invalid_inputs_exit_two[argv1..3]` fail |
| m1 reference without BOM stripping | only the BOM/trim/comments/duplicate test fails |
| m2 reference without trimming | only `test_new_signature_and_compatibility_shim` fails |
| m2 reference plus a test that imports the promised shim | only `test_no_stale_internal_imports_or_exports` fails |
| m3 reference whose `json_store.py` does not `import os` (still atomic) | only `test_failed_replace_rolls_back` fails |
| m3 reference using `Path.replace` | passes (it calls `os.replace`) |
| m3 reference treating an empty delta as a no-op | only `test_invalid_inputs[a-r-delta2]` fails |

## Categories used by the classifier

`scripts/bench/large_task_failures.py` assigns each hidden test, or one case of
a parametrized test, one category. Only a **specified** failure is, by itself,
evidence that a run did not do what was asked. The others are not false
failures either: the grader output cannot attribute them.

| Category | Meaning | v1 tests |
|---|---|---|
| specified | every assertion follows from the prompt or starter behavior | m1 `invalid_syntax`, `empty_input_and_precedence…`, `values_keep_equals…`; m2 `all_callers…`; m3 `idempotence…`, `restart…`, `invalid_inputs[-r-delta0, a--delta1]`; m4 `report_json…`, `total_sort_and_tax` |
| mixed | stated behavior shares a test with unstated behavior or mechanism | m1 BOM/trim/comments/duplicates; m2 signature/shim; m2 stale-import scan; m3 failed-replace rollback; m4 invalid input exit 2 |
| underspecified | only unstated behavior | m2 whitespace-only name rejected; m3 `invalid_inputs[a-r-delta2]` (empty delta) |
| contradictory | prompt, starter public test and hidden test cannot all hold | m4 `legacy_total_still_works` |

Two judgment calls are recorded here so they can be overruled. Rejecting an
empty scope or request ID is taken as the minimal meaning of "must validate
input". m1's `token=a=b=c` case is specified because the starter already splits
on the first `=`.

## v2 contract, task by task

Each row names the conflict, the alternatives, and the recommended behavior.
Every recommendation is applied to the prompt, the starter (only where it
defines legacy behavior), the public test, the hidden tests and the reference
together.

### m1-config-parser

| Item | v1 conflict | Alternatives | Recommendation |
|---|---|---|---|
| Byte-order mark | Hidden input starts with U+FEFF; prompt says only "UTF-8" | strip one leading BOM; reject it; keep it in the first key | Strip one leading BOM. Prompt: "Ignore a leading UTF-8 byte-order mark." Own hidden test. |
| Mixed test | BOM, trimming, comments and duplicates share one assertion | keep; split | Split into one test per stated rule. |
| `=` inside values | Unstated, but starter behavior | state it; leave implicit | State it: "Only the first `=` separates key and value." |
| Deterministic CLI | Stated, never tested | test it; drop the clause | State the order ("keys in file order, last duplicate wins") and add a hidden test of `config_cli.main`. |

### m2-public-api-migration

| Item | v1 conflict | Alternatives | Recommendation |
|---|---|---|---|
| Trimming and uppercase | Hidden expects `render_user(" Ada ", uppercase=True) == "ADA (active)"`; unstated | state both; drop them from the test | State: "Strip surrounding whitespace from the name; `uppercase` applies to the name only." Separate test from signature/shim/re-export. |
| Whitespace-only name | Starter accepts `"   "`; prompt says "preserve validation"; hidden rejects it | state stricter validation; keep starter validation | State: "Reject a name that is empty after stripping (ValueError)." Consistent with trimming. |
| Stale-import scan | Also fails a test that imports the shim the prompt promises to keep | exempt tests; forbid shim imports everywhere and say so | Scan only `userlib/` and `cli.py`; keep `__all__ == ["render_user"]`. |
| Public test | Starter test imports `format_user` from `userlib`, which the prompt removes | keep (a real migration step) | Keep, and record `requires_existing_test_changes: true`. Prompt already says "update … integration test". |
| Caller test | Passes even for unmigrated callers | strengthen; keep | Keep as-is; the import scan covers migration. Note its weakness. |

### m3-state-persistence

| Item | v1 conflict | Alternatives | Recommendation |
|---|---|---|---|
| Empty delta | Hidden requires ValueError; prompt says only "validate input" | reject; no-op recorded; no-op unrecorded | Reject. Prompt: "scope and request_id are non-empty strings; delta is a non-empty mapping of non-empty string keys to integers." |
| Rollback test coupling | Patches `state_persistence.json_store.os.replace`, so `json_store.py` must import `os` | patch `os.replace` globally; state the mechanism | Both: the prompt says "write a temporary file and `os.replace` it", and the test patches `os.replace` itself, so any module path works. |
| Duplicate request and history | Hidden expects a repeated request to leave history unchanged; implied by "idempotent" | state; leave implied | State: "A repeated request changes neither values nor history." |

### m4-cli-feature

| Item | v1 conflict | Alternatives | Recommendation |
|---|---|---|---|
| Legacy `total` | Starter and public test add all arguments (`10 2` → `12.00`); reference and hidden multiply pairs (`10 2 5 3` → `35.00`); prompt says "preserve" | (a) preserve addition; (b) declare a breaking change to price × quantity pairs | (a) Preserve. Prompt: "Preserve the legacy `total NUMBER ...` command: it prints the sum of its arguments, without tax." Hidden: `total 10 2 5 3` → `20.00`. Reference keeps the starter's `total`. |
| Exit status 2 | Hidden requires `SystemExit(2)` from `main()`; a `main()` returning 2 also exits 2 as a process | state the mechanism; accept both | Accept both: the test treats a return value of 2 or `SystemExit(2)` as a pass. |

## Acceptance checks for v2 fixtures

Before any v2 result counts:

1. New IDs (`m1-config-parser-v2`, …), a new manifest, new hashes; v1 untouched.
2. Each starter fails the hidden tests; each reference passes hidden and public.
3. One hidden test per stated requirement. No test mixes stated and unstated
   behavior. A written table maps every prompt clause to its tests and every
   hidden assertion to a prompt clause or starter behavior.
4. Recorded alternative-but-valid implementations pass (for example, m3 with
   `Path.replace`, m4 with `return 2`), and the probe variants above fail only
   the intended test.
5. The classifier's `REQUIREMENTS` table for v2 has no `mixed`, `underspecified`
   or `contradictory` entries.

## What the historical results still support

Trustworthy, because they do not depend on the large-task graders:

- Small-task (t1–t8) pass rates, which these graders do not affect. They were
  not re-audited here.
- Efficiency findings: token, request, cache and reminder measurements,
  including the 61% uncached-input share after the requirement reminder on
  small tasks.
- Run-level facts: stop reasons, stream cuts, retries and usage gaps.
- That no run of either harness passed any large task, as a statement about
  these graders.

To withdraw or downgrade:

- Large-task success (0/12 per harness, and 0 of 27 per family in the GPT-6
  Luna population) as a measure of coding ability. Composite success should be
  read through the small-task stratum only.
- "Accuracy tied with Codex" on large tasks: both are bounded by the same
  graders.
- "After a partial fix the public test passes, so the gate is satisfied and the
  model stops" (readiness plan §0.2) as an established cause. It is a
  hypothesis until specified-requirement failures are counted.
- benchmark-integrity.md's reading of the six m3 rollback failures as
  "genuine": the test depends on `json_store.py` importing `os`, so those
  failures are indeterminate.
- The opposite overstatement as well: grader defects do not explain every
  zero. m4's legacy test is contradictory only for runs that preserved the
  legacy command. m1 and m2 failures fall in mixed tests. m3 has specified
  tests that can fail. Counting specified failures per run is the open question.

## Smallest fair comparison after v2 is validated

Not started; scope needs approval. Subscription use falls on both harnesses.

- **Arms:** DaVinci (current main, product defaults) and Codex CLI. Same model
  and effort (`gpt-6-luna`, high), same machine, the subscription route, print
  mode, interleaved task × repetition × harness order.
- **Development set:** the four v2 tasks × 3 repetitions × 2 harnesses = 24 runs.
- **Protected holdout:** four new tasks written by someone other than whoever
  tunes DaVinci. Stored outside the repository in the existing private-suite
  format (`private_suite.py`), recorded only by hash, run once after
  development results are frozen, never used for tuning. 4 × 3 × 2 = 24 runs.
- **Primary metric:** verified success (the harness's existing task-success
  definition with v2 graders), split by development and holdout.
- **Secondary metrics:** fraction of hidden requirements passed per run; false
  completion (a final answer while hidden tests fail); uncached input, total
  input and output tokens **per verified success**; requests per verified
  success; time to verified completion; unrelated edits.
- **Rules:** failed and stopped attempts stay in denominators; unknown usage
  stays unknown; whole-task cluster bootstrap. With eight task families the
  result can show direction only. A superiority claim needs the much larger
  suite that `docs/competitor-benchmarks.md` requires.
